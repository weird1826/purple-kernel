## M1 - Windows Architecture

### What makes an operating system necessary?

To make this question easily answerable, let's strip down all our understanding of the complexities behind what a computer is.

You have written a computer program that reads a file from the disk. The disk has a set of hardware registers, one DMA Controller, and one interrupt line. Assuming that there is not a layer of abstraction, then our program can talk directly with the hardware, and so can any other program. There is a very high possibility, that two similar programs running almost simultaneously attempting to access the same file can destroy each other's transfers. Your program may also have bugs, for example, one might accidentally write to a random memory address. If there are no guardrails, it can overwrite the memory address where the OS lives, overwriting the OS itself, or maybe the screen bugger, or someone else's data, anything.

A computer without an OS is like a machine where every running program is a Russian roulette with every other program, all the time. Having an OS ends this game, by being the only thing allowed to interact with the hardware, and by doing it in such a good fashion, that every programming running above it has the illusion of exclusive ownership of the entire machine.

Describing is much easier than implementing. Hence, we must think of how can we enforce such things? A rule in software can be broken by a software. What stops a program from simply calling the hardware directly? Or writing memory it does not own? Well, the head of such decisions is CPU.

### CPU Rings and Hardware-enforced Privilege

Every modern x86/x64 CPU has a hardware-feature, called Privilege Rings, built directly into the silicon. These act as boundaries for certain OS components and define what components can have what kind of privilege. The most important are Ring 0 and 3. Ring 0 is the innermost ring and the code running inside it can execute any CPU instruction, access any physical memory address, and configure any hardware register. Ring 3 is the outer wall. The code here cannot directly access the hardware, or perform anything which Ring 0 can do without any restrictions. If it still tries to do so, CPU raises an exception.

Windows uses only two of the four rings the architecture provides. Ring 0 is the kernel and Ring 3 is everything else the OS has. This is not a policy that can be overridden from software; this is physics, i.e., the transistors inside the CPU enforce it.

User mode refers to Ring 3 and Kernel mode refers to Ring 0.

#### Understanding the layers - Bottom to Top

**HAL** (Hardware Abstraction Layer) provides an interface between kernel components and machine hardware. Its job is so that the kernel does not need to know platform-specific details such as interrupt controllers, I/O mechanisms, timers, and multiprocessor hardware; so that much of the OS can remain portable across different hardware configurations. It does not abstract all processor-architecture differences, hence, porting Windows to a new CPU architecture does require change to the kernel and other architecture-dependent code as well as the HAL.

Above HAL, there is NT Kernel, the low-level core of `ntoskrnl.exe`. The kernel is responsible for core mechanisms such as thread scheduling and dispatching, interrupt and exception handling, and multiprocessor synchronization. It is slim, has relatively little policy (it provides low-level mechanisms on which security depends) and does not have high-level OS functionality. Functions like file and I/O management, memory management, process management, and security-related services are primarily provided by the **Executive**, which uses the kernel's supply of low-level mechanisms to implement higher-level services.

**Executive** is also within `ntoskrnl.exe`. Think of it as a collection of "managers", each responsible for one domain, e.g., Process Manager creates and tracks processes, Memory manager maps virtual addresses to physical RAM, I/O Manager routes file and device operations through a stack of drivers, Object Manager issues handles, and Security Reference Monitor performs every access check in the system. These all are written in the same binary but act as a distinct components. Security checking is shared among the relevant managers and, where necessary, drivers rather than being performed exclusively by SRM. _Note: the mentioned managers do much more than what is written. the mentioned functionalities is just to understand the concept._

**Kernel-mode Drivers (`.sys` files)** also run in ring 0 and have highly privileged access to OS. Security vendors for AVs, or EDRs, use a combination of user mode components and kernel mode drivers. Without Ring 0 access, they cannot intercept operations early enough to be useful. Windows Driver Model defines how drivers can be integrated in the kernel. Any vulnerability in such drivers can have system-wide consequences such as crashes or security compromise.

Above Ring 0, sits `ntdll.dll` in Ring 3. This is one of the most important DLLs in the entire OS from a security telemetry/interception point perspective. It is like a bridge as many Win32 API call such as `CreateFile`, `OpenProcess`, `VirtualAlloc`, etc. flows down through this. Functions in `ntdll.dll` execute system calls which transfer the control to kernel. EDR products intercept API calls in user mode in `ntdll.dll`, by patching function stubs with jump instructions.

Above this, lies Win32 API DLLs such as kernel32.dll, advapi32.dll, user32.dll. These provide the documented APIs that most programs use. They are wrappers that translate Win32 calls into Native API calls, adding parameter validation and error translation.

### Typical System Call Flow

Everytime a user-mode program asks the OS to perform certain operations, this sequence usually executes:

1. User-mode code calls a Win32 API, e.g., `ReadFile`
2. The Win32 implementation eventually invokes a native API entry point in `ntdll.dll`, `NtReadFile`
3. The `ntdll` system-call stub places the SSN (system-service number) into EAX register and prepares the required argument/register state
4. The stub executes the syscall instruction
5. The CPU transitions from Ring 3 to 0 privilege and transfers control to kernel's system call entry point configured by the OS
6. Windows' system call entry/dispatch machinery validates and interprets the service number and selects the appropriate service table/entry
7. The kernel-side implementation executes in Ring 0 and performs the requested operation, **in accordance with** Windows' security and kernel rules
8. The result is returned through the system call return path, normally using `sysret` on x64, and execution resumes in user mode

## M2 - Boot Process

When a device is totally off, nothing exists yet. When we press the power button, the OS must build itself from nothing, generally speaking.

A boot chain is not just a usual sequence of operations launching each other. But it is also a chain of verification. Each stage verifies that the next stage has not been tampered with before handling over control, because, once it does, to a potentially malicious code, everything that comes after is compromised. Microsoft's entire boot security architecture is built around making this chain hard to break.

The actual boot chain is very complex and it is fascinating to read about how many components actually contribute into kickstarting the OS and is best described in Windows Internals Part 2, 7th Ed. It is a good read. However, just for a reference, the boot chain can be very much simplified. This is what **Claude AI** has done in terms of simplification of boot sequence:

In the Phase-3, notice "ELAM", it stands for Early-Launch Anti-Malware. Before Windows 8, a rootkit that registered itself as a boot-start driver (Start=0 in Registry) would load before any AV has a chance to run. ELAM fixed this issue by creating a special driver category called Early-Launch that loads before all third-party drivers. Windows Defender's ELAM driver (`WdBoot.sys`) examines every other boot-start driver as it loads and classifies it as _known good_, _known bad_, or _unknown_. The kernel can refuse to load a known bad driver entirely. ELAM reduced the viability of traditional boot-start rootkits, although, it did not eliminate boot kits/rootkits from using other stages and techniques.

**Session 0 Isolation**: Before Windows Vista, services and user applications ran in the same desktop session called Session 1. If a service is compromised, it can directly interact with the user's desktop, which is a classic privilege escalation path known as Shatter attack. Vista introduced Session 0 isolation which mandates that all services must run in Session 0 and with no visible desktop. User sessions start at Session 1 and above. `smss.exe` creates and configures these sessions, but should not be described as a manager of user sessions. On Vista and later, SMSS creates additional instances of itself when configuring sessions, while components such as the Local Session Manager handles session management functions. Just like other processes, `smss.exe` can also be impersonated by attackers, but it can be verified by its location - `%SystemRoot%\System32\smss.exe`, digital signature, process tree, and other properties.

The boot chain has been broken in practice throughout the years. A recent example can be BlackLotus (2023) which was UEFI boot kit that exploited the Secure Boot bypass vulnerability (CVE-2022-21894). This allowed an attacker to roll back the Windows Boot manager to a vulnerable version that was still legitimately signed by Microsoft and had not been revoked in the Secure Boot DBX. Because this vulnerable boot manager remained trusted, Secure Boot did not prevent it from executing. BlackLotus then exploited the boot manager vulnerability to bypass Secure Boot protections and load its malicious boot kit early in the boot process, before Windows was fully initialized.
